## 一、红外对管（TCRT5000）原理与应用

### 1.1 工作原理

红外传感器基于红外线的反射原理工作。红外线照射到物体表面时，部分被吸收，部分被反射。传感器由发射器和接收器两部分组成：

- **发射器**：发射一束红外线照射到物体表面
- **接收器**：接收反射回来的红外线，将信号传输至控制器

输出信号与物体表面颜色的关系：

| 表面颜色 | 反射强度 | 接收信号 |
|---------|---------|---------|
| 白色/亮色 | 较强 | 较大 |
| 黑色/暗色 | 较弱 | 较小 |

### 1.2 QST小车应用

红外对管安装在车底部，通过检测地面黑线或白线实现循迹功能。接收端同时连接 Hi3861（IO13、IO14）和 STM32（PA11、PA12），便于后续扩展开发。

## 二、软件定时器（Software Timer）

### 2.1 基本概念

软件定时器基于系统 Tick 时钟中断，由软件模拟实现。经过设定的 Tick 计数值后触发用户定义的回调函数。其定时精度与系统 Tick 时钟周期相关。

> **注**：硬件定时器数量有限，无法满足多定时业务需求，软件定时器扩展了可用定时器数量。

### 2.2 支持功能

1. 静态裁剪：可通过宏配置关闭软件定时器功能
2. 软件定时器创建（`osTimerNew`）
3. 软件定时器启动（`osTimerStart`）
4. 软件定时器停止（`osTimerStop`）
5. 软件定时器删除（`osTimerDelete`）
6. 软件定时器剩余 Tick 数获取

### 2.3 运作机制

软件定时器使用系统的一个队列和一个任务资源，遵循 FIFO 规则：

1. 定时器以 Tick 为基本计时单位
2. 创建并启动时，内核根据当前系统 Tick 时间及定时间隔确定到期 Tick 时间
3. 定时器控制结构挂入计时全局链表
4. Tick 中断到来时，扫描全局链表，记录超时定时器
5. Tick 中断结束后，最高优先级的软件定时器任务被唤醒，调用超时回调函数

**定时器触发顺序**：定时短的定时器优先于定时长的定时器被触发。

## 三、软件定时器 API

### 3.1 osTimerNew —— 创建定时器

> ⚠️ 不可在中断服务函数中调用

| 项目 | 说明 |
|------|------|
| **函数原型** | `osTimerId_t osTimerNew(osTimerFunc_t func, osTimerType_t type, void *argument, const osTimerAttr_t *attr)` |
| **参数** | `func`: 回调函数指针<br>`type`: 定时器类型（`osTimerOnce` 单次 / `osTimerPeriodic` 周期）<br>`argument`: 回调函数参数<br>`attr`: 定时器属性 |
| **返回值** | 定时器 ID |

### 3.2 osTimerStart —— 启动定时器

| 项目 | 说明 |
|------|------|
| **函数原型** | `osStatus_t osTimerStart(osTimerId_t timer_id, uint32_t ticks)` |
| **参数** | `timer_id`: 定时器 ID<br>`ticks`: Tick 计数值 |
| **返回值** | `0` 成功，非 `0` 失败 |

### 3.3 osTimerStop —— 停止定时器

| 项目 | 说明 |
|------|------|
| **函数原型** | `osStatus_t osTimerStop(osTimerId_t timer_id)` |
| **参数** | `timer_id`: 定时器 ID |
| **返回值** | `0` 成功，非 `0` 失败 |

### 3.4 osTimerDelete —— 删除定时器

| 项目 | 说明 |
|------|------|
| **函数原型** | `osStatus_t osTimerDelete(osTimerId_t timer_id)` |
| **参数** | `timer_id`: 定时器 ID |
| **返回值** | `0` 成功，非 `0` 失败 |

## 四、AP3216C 三合一环境传感器

### 4.1 概述

AP3216C 是一款三合一环境传感器，内部集成：

- **ALS（数字环境光传感器）**
- **PS（距离传感器）**
- **IR LED（红外 LED）**

芯片通过 **I2C 接口** 与 Hi3861 通信。

### 4.2 硬件连接

AP3216C 与 Hi3861 通过 I2C 总线连接（参考开发板电路原理图）。

## 五、任务函数命名规范（重要）

多任务系统中，不同模块的任务函数名称必须唯一，否则会导致链接时出现 `multiple definition` 错误。

### 各模块任务函数命名对照表

| 模块 | 原函数名 | 修改后 |
|------|---------|--------|
| Hello_World | `thread1` / `thread2` | `HelloWorldThread1` / `HelloWorldThread2` |
| TCRT5000 | `TCRTTask` | 保留（已唯一） |
| SG90 舵机 | `thread1` / `thread2` / `thread3` | `SG90Thread1` / `SG90Thread2` / `SG90Thread3` |
| HC-SR04 | `Hcsrtext` | `Hcsr04Task` |
| SSD1306 OLED | `Task1` | `Ssd1306Task` |
| SHT20 | `thread1` / `thread2` / `thread3` | `Sht20Thread1` / `Sht20Thread2` / `Sht20Thread3` |
| AP3216C | `Task1` | `Ap3216cTask` |

### 5.2 修改要点

1. 任务函数名称唯一化
2. `osThreadAttr_t` 中的 `.name` 字段相应修改
3. `osThreadNew()` 中的函数指针同步更新
4. 错误日志信息中的任务名称同步修改

## 六、编译错误汇总

### 6.1 Error: Invalid token（BUILD.gn 语法错误）

**原因**：GN 文件中使用了多余的分号 `;`

**解决**：删除 `sources = [...]` 后面的分号

```gn
# 错误写法
sources = [
    "file.c"
];   # ← 多余分号

# 正确写法
sources = [
    "file.c"
]
